# 坐姿提醒 · P0 原型

在**本机**本地跑通「采集 → 姿态推理 → 判定 → 语音提醒」全链路。
推理全程本地，不依赖任何远程算力。

> 📖 **纯侧面方案（当前采用）见 [`../../docs/03-side-only-plan.md`](../../docs/03-side-only-plan.md)**
> 📖 调研依据见 `../../docs/01-research-report.md`，现场部署见 `../../docs/02-deployment-taskbook.md`
> 本文只做速查。

## 图形界面（给孩子用）· 推荐入口

**双击项目根目录的 `启动坐姿小卫士.bat`** 即可，不弹控制台窗口。

| 文件 | 用途 |
|---|---|
| `启动坐姿小卫士.bat` | 正常使用。`pythonw` 启动，无黑框 |
| `调试模式.bat` | 程序打不开时用，保留控制台便于看报错 |
| `演示模式.bat` | 不接摄像头，循环展示「坐得好／提醒／看不到人」三种状态，**语音提醒也会播** |

> 演示模式**会出声**——它是用来预览真实体验的，不出声就没法完成报告 §7
> 「让孩子听一遍，确认不刺耳、不反感」这一步。
> 若点了 `演示模式.bat` 却没声音：先看主界面「声音」按钮显示的是"开"还是"关"，
> 再看系统音量。也可以在「家长设置 → 提醒与声音」里逐个**试听**语音片段。

### 窗口尺寸会按屏幕自动收敛（HDPI 注意）

实测这台笔记本：**1920×1080 物理屏开 150% 缩放 → Qt 的逻辑桌面只有 1280×720，
可用高度仅 680**。窗口尺寸写死会直接超出屏幕（标题栏被顶出、底部按钮被任务栏压住）。

> 📌 **本机实测（2026-09-26，`--screen`）**：逻辑桌面 **1920×1080**、可用区域 **1920×1032**、
> 缩放 **2.00x** —— 高度充足，不会出现上面那种被压住的情况。下面这套自适应逻辑仍然保留，
> 它是给"换到更小/更缩放的屏幕"兜底的。

所以初始尺寸按 `availableGeometry()` 收敛，并用屏幕可用区域居中；最小尺寸设为 700×500。
如果你在别的机器上看到窗口装不下，先跑这条查真实屏幕参数：

```bash
envs\posture\Scripts\python.exe posture_app.py --screen
```

它会打印「逻辑几何 / 可用区域 / 缩放」三项，一眼能看出是不是缩放问题。

⚠️ **别用 `--selftest` 查屏幕参数** —— 它强制走离屏（offscreen）平台，
报的是 800×800 的假数据，会把人带偏。`--selftest` 是用来验界面代码的，不是验屏幕的。


界面设计（依据报告 §8 的儿童场景研究）：

| 原则 | 做法 |
|---|---|
| 零操作启动 | 双击即开始监测，孩子不需要按任何按钮 |
| 先看脸色再看字 | 状态用大色块 + **手绘表情**（Canvas 画，不用 emoji，避免字体差异变方块） |
| **不用红色** | 警示用暖橙。红 = 惩罚感，会让孩子想关掉程序 |
| 正向激励 | 坐得好时绿色大字「坐得真棒！」，"坐得好的时间／良好率／连续良好"放在最显眼处 |
| **空格键暂停/继续** | 不用去点按钮。⚠️ 底部按钮设成不可获得焦点 —— Qt 默认把空格当"点击"焦点按钮，不设的话空格会被抢走 |
| 设置隔离 | 阈值、标定、提醒节奏全在「家长设置」里，孩子界面看不到 |

技术结构：界面与引擎**分线程、分模块**，两者只靠 `engine.snapshot()` 通信
（推理放主线程会让界面在最关键时刻卡死）。2026-10-18 重构后，实现全在 `posture/` 包里，
仓库根那三个 `posture_*.py` 只剩转发用的壳 —— 见下面「代码结构」。
摄像头归 `posture/camera.py`：它自己有**一条长命采集线程**，开流、重试、掉线重连都在里面，
引擎只负责「取最新帧 → 推理 → 判定 → 提醒」。

### 阈值标定：靠「审核判定」页收数据，不要靠录视频

任务书 §6 原本写的是「录 15~20 分钟视频 → 人工逐帧标注 → 扫阈值」。**这条路走不通**：
逐帧标注 15 分钟视频的成本太高，家长不会做，而「误报率 < 10%」这个验收指标
就永远算不出来。

改成**在使用中顺手标注**：

1. 引擎在**每次提醒时**自动存一张现场图（含当时的指标与基线）
2. 另外按固定间隔（默认 3 分钟）存一张「判为良好」的抽样
3. 家长在「家长设置 → 审核判定」里逐条点「对／不对」
4. 「审核判定」页底部直接用你已审核的样本**反推建议阈值**

⚠️ **能力边界（界面里也写着）**：

| | 说明 |
|---|---|
| ✅ 能发现**误报** | 判「歪了」其实坐得好 |
| ❌ 发现不了**漏报** | 漏报时程序压根没存图 —— 所以才要存那些「判为良好」的抽样来查漏 |

还有一条**归因规则**：一条样本只用来调**它自己触发的那个指标**。
家长标「确实歪了」可能是因为塌腰，而那一帧的 `neck_angle` 可能很低 ——
拿它去压 `neck_angle` 的阈值就是错的。

**这套数据只能用来调阈值，不能用来重训练模型**（两者完全不同）：

| | 调阈值 | 重训练模型 |
|---|---|---|
| 改什么 | 判定规则（12° → 16°） | 关键点模型本身 |
| 数据量 | 几十条 | 几百~几千张 |
| 标签 | 「对／不对」决策标签 | **每个关键点的 (x,y) 坐标** |
| 人工 | 每条 2 秒 | 每张 1~2 分钟 |
| 跑在哪 | 本机，秒级 | 训练平台，小时级 |

存的是 480px 缩略图，且只有决策标签 —— 没有关键点真值，**不能用于训练**。
（`review_keep_fullres` 控制是否为「提醒现场」另存一张**原图**。
2026-09-26 按用户的"处处用最高清"**改成默认开启**：留一张原图等于把
"以后还能不能做模型微调"这个选项保住 —— 那些帧是回不来的。
原图按当前采集档取（现为 4K，约 1~3MB/张）。
代价是原图也计入 `review_max_files`，可留存的条数会变少；想省空间就在界面上关掉。）

**隐私**：全部存本机 `review\` 目录、不上传；上限默认 300 条（超出自动删最旧的，
且优先删未审核的，保证标注不丢）；「审核判定」页有**一键清空**。

### 摆好机位后，先用「家长设置 > 机位检查」确认


定位问题的失败方式是**静默的**：把摄像头正对孩子，程序不报错、不崩溃，
但**永远不提醒**——因为正面视角下同侧的耳和肩几乎在一条竖直线上，
前后关系被压扁，`neck_angle` 恒接近 0。

所以「机位检查」页给出量化确认：点「开始观察」，**让孩子往前伸一下头再坐回去**，
看「颈部前倾角摆幅」涨到多少：

| 摆幅 | 判定 |
|---|---|
| ≥ 10° | ✅ 机位没问题，前后关系确实测得到 |
| 5~10° | ⚠️ 勉强可用，建议再往侧面转一点 |
| < 5° | ❌ 摄像头太正对孩子了，转到 80~90° 正侧 |

两个设计选择，都不是随手定的：

1. **判据用「摆幅」而不是「当前值」** —— 家长多半在孩子正常坐着时打开这一页，
   当前值天然正常，拿它判会误报"机位不对"。
2. **判据用「摆幅」而不是「相对基线的差值」** —— 摆幅不需要基线，
   所以**不用等标定跑完就能验机位**（标定要 10 秒且需要孩子坐正，
   先验机位再标定，顺序更顺）。

## 摄像头子系统（2026-10-18 重构）

"加载很久""画面只有四分之一""有时能开有时不能"三条投诉都归这里。
实现全部在 `posture/camera.py`（1300+ 行，一半是注释里踩过的坑），入口只有一个：
**`CameraStream` —— 一条长命采集线程**。

### 两条口径（用户定的，代码不许自作主张）

| 口径 | 落到代码上 |
|---|---|
| **4K 优先、不许静默降档** | `tier_ladder(requested)` 的第一档**永远是请求档**（默认 3840×2160）。低档只在请求档确认拿不到画面后才轮到；一旦落到低档，`OpenResult.degraded=True` + `warnings` 必须非空，界面必须显示 |
| **加载不许没上限** | 开流有总预算 `OPEN_BUDGET_SEC=15s`，到点明确报错并列出试过的每个组合 —— 不再出现 31s/48.9s 那种无上限等待 |

### 实测计时（`--bench-open`，本机 DSHOW / USB 2.0 Camera / 4K MJPG）

| | 重构前 | 重构后 |
|---|---|---|
| 中位 | 10.6s | **1.7~3.7s** |
| p95 / 最差 | 48.9s（曾无上限） | **4.9~9.2s** |
| 成功率 | 有失败率、失败后界面僵住 | 18/18 轮，全部 **3840×2160**（零降档、零失败） |

两批实测（`--bench-open 12` + `--bench-open 6`）里**每批第一轮最慢**（9.15s／7 次尝试，
其余各 1 次就成）。原因是设备刚被上一个进程放开、驱动还在收尾，属于设备状态而不是代码缺陷；
`尝试=7 次`恰好证明准入闸按一档一档试、没有越预算。这也是为什么界面要把
"已经等了 N 秒，正在试 DSHOW ／ 3840x2160"说出来 —— 慢的时候得有话讲。

复测命令（连续开关 12 次，低于请求档会直接打 `⚠️ 降档`）：

```bash
envs\posture\Scripts\python.exe posture_monitor.py --bench-open 12
```

### 四条关键机制（每条都是实测换来的）

1. **属性在构造函数里协商，不要开完再 `cap.set()`**
   `cv2.VideoCapture(idx, backend, [W, H, FOURCC, MJPG, ...])` 实测 **0.17s**；
   开流成功后再 `set()` 同样三个属性是 **4.46s** —— 差 **26 倍**，这正是"加载很久"的主因。
   ⚠️ MSMF 后端不接受构造期属性表 → 捕获 `TypeError` 退回后设。
   ⚠️ 顺序必须是**先 MJPG 再分辨率**，反了会静默退回 YUY2（USB 2.0 带宽撑不住高档位）。

2. **`read()` 返回 `ok=True` 不等于有画面**
   坏开流返回**全零占位帧**（每帧固定 1000ms）。判据用 `frame.max() >= 8`；
   同时必须容许**预热帧**（`warmup_budget()` 按档位给 6/4/2 帧容限），
   容限设小了会把好开流误杀成"设备不可用"。

3. **cap 绑定创建它的线程**（DSHOW 走 COM）
   实测 2×2：在工作线程创建 → **0/5 全废**。所以开流与后续读取必须在
   **同一条长命线程**里 —— 这就是 `CameraStream` 存在的理由，别把它拆成"临时线程开流 + 主线程读"。

4. **可疑后端用子进程探测，结果落盘**
   MSMF 的构造函数会**无限阻塞**，线程超时救不回来（线程杀不掉），
   所以起子进程试、可硬杀。结论写进 `camera_profile.json`，
   **一个组合一辈子最多付一次探测代价**（下次启动直接跳过，省掉实测 16s 的白烧）。

⚠️ 还有一条**反效果的设计别再犯**：把 profile 做成"阶段 0 预检"（先预检一遍再走阶梯），
同一个组合要付两次坏开流代价，实测把中位数拖回 10.6s。profile 只用来**决定试的顺序**，
不用来跳过验证。

### 预算是「准入闸」，不是「事后截断」

`deadline` 只在"每次读帧之前"起作用，管不住一轮尝试的**起点**：
真机出现过「预算 15s、22.35s 才报错」—— 起点是预算快用完时才想起去探 MSMF。
所以剩余预算 `< MIN_ATTEMPT_SEC(2.5s)` 就**不再开始**新一轮、不再起探测。
最坏情况 = 预算 + 一次读帧超时，可解释、可复述。

### 掉线之后会发生什么（重构前这里根本没有恢复路径）

```
CameraStream: 心跳 > STALL_SEC(6s) 没新帧 → phase=reconnecting → 同线程重开
                                                  ↓ 成功                ↓ 失败
                                          reconnects+1，继续采      REOPEN_DELAY_SEC(3s) 退避后重试
```

引擎侧的三条契约（测试组 N 锁住）：
- 断线期间**统计与判定都暂停** —— 否则会把"没画面"的时间算进"坐得好的时间"；
- 界面文案说「正在自动重连」，**不许**说成"看不到你啦"（那是设备问题，不该算在孩子头上）；
- **档位一变就作废基线重标** —— `sh_ear_len` 是像素长度，4K 标的基线拿到 1080p 下用会
  静默判不出「低头」（漏报，且完全看不见）。同档重连则不许白白重标一次。

### 界面上的三处呈现

| 位置 | 说什么 |
|---|---|
| 主界面状态卡 | 开流期间「已经等了 N 秒，正在试 DSHOW ／ 3840x2160 ／ 摄像头 0 第 2 轮」；断线时「正在自动重连（第 n 次）」 |
| 主界面黄色横幅 `#camWarn` | 只在**降档**或**断线**时出现。降档用暖橙、断线用灰蓝，**两种都不许用红**（红=惩罚感，孩子会想关掉程序）；平时整条隐藏 |
| 家长设置 → 机位检查 | 设备实况一行：后端 / 索引 / **实际** WxH / 状态 / ⚠️ 低于请求档位 / 已自动重连 n 次 + 每条警告原文 |

### 本机档案 `camera_profile.json`

记录上次成功的组合、各后端的探测结论、各档位能不能拿到画面。
它是**本机硬件指纹**（换摄像头/换机器就是废数据），所以：
- **已进 `.gitignore`**，与 `config.json`、`baseline.json`、`review/` 同级（孩子照片不外传的约束一起管）
- 结论可疑（换设备、频繁失败）时**删掉它重测**，或跑 `posture_monitor.py --list-cameras`
- 它**不会**把降档结果写回 `config.json` —— 下次启动仍然先试 4K（见上表口径）

⚠️ **启动开流失败时故意没有"自动重试"**（和上面的自动重连区分开）：这种失败多半是设备正被
别的东西占着，或撞上了 UVC 的占位态 —— 自动重试要么同样失败，要么让人白等一整个预算
（再 15 秒、没有任何新信息）。所以现在的行为是**明确报错 + 排查顺序 + 界面「重试」按钮**：
看得见原因，比默默多等 15 秒更好沟通。**开成功之后**的掉线才交给自动重连管。
这条决定由离线用例 **N35-N40** 锁着（失败必须落 `error`、`CameraStream` 只 new 一次、
错误分支里不许出现 `.start(`、退出时把设备让出来）—— 想改成自动重试，先让那几条红。

## 快速开始

```bash
# 0) 环境
python -m venv envs\posture
envs\posture\Scripts\python.exe -m pip install opencv-python==5.0.0.93 numpy==2.5.3 PySide6-Essentials==6.11.2   # 完整步骤与理由见 requirements.txt

# 1) 排查第一步：看系统认到了几颗摄像头
envs\posture\Scripts\python.exe posture_monitor.py --list-cameras

# 2) 性能自测 —— 必须让一个人坐在摄像头前，否则数字偏乐观 40%
envs\posture\Scripts\python.exe posture_monitor.py --bench --bench-frames 100

# 3) 纯侧面试跑（⚠️ 摄像头要垫高到孩子头部高度：1.0~1.1m）
envs\posture\Scripts\python.exe posture_monitor.py --side-only --camera 0 --calib 10

# 4) 双机位（有第二颗摄像头时）
envs\posture\Scripts\python.exe posture_monitor.py --camera 0 --camera2 1 --calib 10
```

按 `q` 退出。

## 参数

| 参数 | 用途 |
|---|---|
| `--list-cameras` | 列出可用摄像头（**排查第一步**） |
| **`--bench-open 12`** | **开流计时验收**：连续开关 N 次，打印每轮耗时 + 中位/p95/最差/失败，并按验收线（中位 ≤8s、p95 ≤15s）给结论；**低于请求档会直接打 `⚠️ 降档`**，顺带验"有没有静默降档" |
| `--bench --bench-frames 100` | 性能自测（**需真人入画**） |
| `--side-only` | **纯侧面单路模式**（纸笔作业推荐） |
| `--camera N` | 主路索引；`--side-only` 时指侧面机位 |
| `--camera2 N` | 第二路（侧面）索引；给了就启用双机位。与 `--side-only` 互斥 |
| `--side-yaw 90` | 侧向机位偏航角（度）：0=正对，90=正侧。**建议 80~90，不要用 45** |
| `--backend DSHOW` | 强制指定采集后端（默认 DSHOW→MSMF→ANY 依次试）。**换摄像头后要重测**：新摄像头只有 DSHOW 可用，MSMF 会卡死 |
| `--calib 10` | 标定时长（秒） |
| `--model pose_landmarker_full.task` | 换更高精度档位（一般不需要） |
| `--no-window` | 不开预览窗（长期挂机） |
| **`--video 录像.mp4`** | **离线复现判定**：不接摄像头，把一段录像跑完整条判定链并输出逐条时间线（配 `--calib` 用录像前段标定，`--calib 0` 则用现有 baseline.json）。**跑得比真实播放快，且结果可复现** |

## 离线自检（不需要摄像头、不需要依赖）

```bash
python tests/test_offline.py
```

用合成关键点回归判定逻辑，**298 个用例**，改代码后先跑这个：

| 组 | 覆盖 |
|---|---|
| A | 正面指标与判定（含「靠近摄像头只报太近、不误报低头」） |
| B | 侧面指标与判定（**含宽高比校正与偏航补偿的回归锁**） |
| C | 误检帧筛除 / 基线健壮性 |
| D | 双机位融合 |
| E | **迟滞与两道提醒间隔**（含「恢复期界面不闪」「换原因也照样拦」的回归锁） |
| F | 标定结果自检的分级 |
| G | **阈值建议**（人工审核样本 → 建议阈值，含"误报权重更高"） |
| H | **坐正了不发声**（源码级锁：这条约束没有摄像头没法做行为测试） |
| I | 采集档位 / 日志落盘 |
| J | Windows SAC 拦 matplotlib 的兜底 |
| K | 摄像头开流鲁棒性（旧实现踩过的坑，锁住不许改回去） |
| L | **HiDPI 预览铺满**（"画面只有四分之一"的回归锁） |
| M | **摄像头子系统纯逻辑**（档位阶梯 / 预算与准入闸 / 有效帧 / 探测与 profile / 采集线程归属） |
| N | **引擎 × 设备状态机**（假采集线程跑真引擎：降档上报、基线绑定实际分辨率、断线暂停、重连重标、**开流失败不自动重试**） |

⚠️ 其中 K/L/M/N 几组是**源码级锁**（读 `posture/*.py` 的文本比对）。
它们不证明"跑得对"，只证明"某些顺序与约束没被无意改掉"——
所以**函数改名/搬家时测试会红**，那是设计如此：先对着实现改锁，别删。
组内还有一条**执行顺序**约定：N 组会改判定用的模块全局，必须最后跑。

界面另有一套冒烟自检（26 项，含审核存图标注闭环、摄像头状态渲染 7 项、坐正不发声的行为验证），不需要摄像头：

```bash

```

## 指标一览

### 侧面（像素空间算角度，已做宽高比 + 偏航校正）

| 指标 | 含义 | 阈值（相对基线） |
|---|---|---|
| `neck_angle` | 肩→耳 与竖直方向夹角 | +12° → **头前倾** |
| `trunk_angle` | 髋→肩 与竖直方向夹角（需髋可见） | +8° → **塌腰** |
| `sh_ear_len` | 肩→耳 直线距离 | 收缩 12% → **低头** |

### 正面（按肩宽归一化）

| 指标 | 含义 | 阈值（相对基线） |
|---|---|---|
| `head_drop` | 耳-肩垂直距离 / 肩宽 | 收缩 10% → 低头 |
| `head_tilt` | 双耳高度差 / 肩宽 | +0.06 → 歪头 |
| `shoulder` | 双肩高度差 / 肩宽 | +0.05 → 歪肩 |
| `span` | 肩宽绝对值 | 膨胀 15% → 太近 |

**为什么正面能忽略宽高比、侧面不能**
正面所有指标都**除以肩宽**，宽高比的影响在「当前值 / 基线」这一步自然抵消；
侧面左右肩在画面里几乎重合，**肩宽不可用**，只能靠角度——角度对宽高比是敏感的，
不校正就会被压扁（16:9 下少 44%）。

| 坐姿问题 | 正面 | 侧面 | 纯侧面模式 |
|---|---|---|---|
| 头前倾（CVA 颅椎角） | ❌ | ✅ | ✅ |
| 塌腰 | ✅ | ✅ | ✅（需髋可见） |
| 低头 / 趴桌 | ✅ | ✅ | ✅ |
| 歪头 / 歪肩 | ✅ | ❌ | ❌ 已放弃 |
| 距离过近 | ✅ | ❌ | ❌ 纸笔场景不适用 |

这不是模型好坏问题，是几何决定的。必须靠侧面机位。

## 语音提醒

预生成的音频放 `voice/`，按问题命名，**缺失时自动退回系统提示音**：

```
voice\头前倾.wav  voice\塌腰.wav  voice\低头.wav     <- 纯侧面模式用这三个
voice\歪头.wav  voice\歪肩.wav  voice\太近.wav  voice\含胸驼背.wav   <- 双机位模式额外需要
```

**文件优先级：`<问题名>.wav` > `<问题名>.mp3`。** 原因见下。

### 为什么最终存 wav

| | wav（winsound 播） | mp3（只能 MCI 播） |
|---|---|---|
| 播放调用 | `PlaySound(SND_ASYNC)`，**真异步、无设备开关开销** | `mciSendString` 的 open/close 是**阻塞**调用 |
| 并发 | 天然安全 | 别名全局唯一，新播会 `close` 掉**正在播**的那条 |
| 体积 | ~100KB/条 | ~13KB/条 |

体积代价完全可接受（7 条不到 1MB），换来的是播放稳。
**mp3 那条路的坑是实测踩出来的**：频繁触发时新语音不断掐断正在播的，
听感就是"有的没播出来"；而阻塞调用还卡住了采集循环。

### 但语音本身用的是更年轻的神经语音

本机 SAPI5 **只有 `Microsoft Huihui Desktop` 一个中文语音**，是成年女声、机械，
而且没有更年轻的选项。所以用 **edge-tts 的 `zh-CN-XiaoyiNeural`**
（VoiceTag 场景=Cartoon、性格=Lively）—— 中文语音列表里最年轻自然的一个。

edge-tts 只出 mp3，而本机没有 ffmpeg → 用 **`soundfile`**（自带 libsndfile 1.2+，
支持 mp3 解码）转成 wav。**全程不需要外部可执行文件。**

MCI 通道保留着，只作 mp3 的兜底。

### 语速 vs 时长：这是个取舍，不是两个独立旋钮

**语速调慢会让片段变长**，而报告 §7 要求 1~2 秒（孩子正在思考，长句会打断）。
所以"慢"必须用**压短文案**来换：

| | 旧（Huihui） | 新（Xiaoyi） |
|---|---|---|
| 语速设置 | rate=+2（还加快过） | rate=-10%（放慢） |
| 每秒字数 | 0.30 秒/字 | **0.44 秒/字（慢 47%）** |
| 文案长度 | 7 字 | **压到 4~5 字** |
| 实际时长 | 2.1 秒 | **2.0~2.2 秒** |

结论：**单位语速明显变慢了，但总时长没变长** —— 靠砍字换来的。

重新生成（`tools/make_voice.py`）：

```bash
envs\posture\Scripts\python.exe tools\make_voice.py --all           # 神经语音 -> wav
envs\posture\Scripts\python.exe tools\make_voice.py --rate -15%     # 再慢一点
envs\posture\Scripts\python.exe tools\make_voice.py --engine sapi   # 离线兜底（Huihui）
envs\posture\Scripts\python.exe tools\make_voice.py --list          # 看有哪些语音
```

旧的 Huihui wav 已归档到 `voice\sapi-huihui\`（不删，方便 A/B 对比）。
想切回成年女声：把那里的 wav 拷回 `voice\` 覆盖同名文件即可。

**试听入口**：「家长设置 → 提醒与声音」里每个语音片段都有一个按钮，
试听会忽略静音开关（点了没声音会让人以为功能坏了）。
报告 §7 要求"让孩子听一遍，确认不刺耳、不反感"——就靠这个按钮。

## 必须知道的限制

| 限制 | 说明 |
|---|---|
| **阈值未标定** | `THRESHOLDS` / `SIDE_THRESHOLDS` 是初始值，**必须用真实数据回归**，否则误报率不可控 |
| **摄像头高度** | 放桌面时摄像头约 90~97cm，孩子眼睛 100~115cm，属轻度仰拍（5~10°）。**垫高 10~20cm** 更稳，也让髋部更容易入画（塌腰判定需要） |
| 侧向机位别用 45° | 45° 只能看到前后位移的 71%；纯侧面模式请摆 80~90° |
| 儿童关键点抖动 | 通用模型按成人训练，儿童头身比不同。缓解靠个人基线；根治要靠模型微调 |
| 摄像头后端 | ⚠️ **换摄像头会反转结论，所以不能写死**。历史三次实测：笔记本 = DSHOW 可用 / MSMF 报错；旧 USB 摄像头 Nebula 02 = 只有 MSMF 能开、DSHOW 按索引全废；**新摄像头（USB 2.0 Camera）= DSHOW 可用，而 MSMF 连 `cv2.VideoCapture()` 构造函数都会无限阻塞**。程序按「上次成功的后端 → DSHOW → MSMF → ANY」依次试，**真正的判据是"能否读到有效画面"**；可疑后端先用**子进程**探（可硬杀），结论记进 `camera_profile.json`，会卡死的后端整条放弃。**换设备后把 profile 删了重测** |
| 摄像头分辨率 | ⚠️ **逐档实测后才定的档，不照搬旧结论**。新摄像头（USB 2.0 Camera，VID_0C49&PID_636F，**标称 4K**）最终定 **3840×2160 + MJPG**：独立开合 10 轮 **10/10 = 100% 可靠、~14 FPS**。历史沿革（**前两轮结论都是错的，别再照抄**）：曾以为"1080p 是上限"、"720p 是甜点"，那都是 **YUY2 未压缩** 造成的假象 —— 见下一行 |
| ★ **像素格式（FOURCC）才是关键** | OpenCV/DSHOW 默认协商 **YUY2 未压缩**，USB 2.0 带宽仅 ~35MB/s，每帧 `w×h×2` 字节：720p 就 1.8MB（开流成功率掉到 60%）、1080p 4MB（只剩 3.3 FPS）。**切 MJPG 后 4K 反而 100% 可靠**。→ 设置顺序**必须**「先 `CAP_PROP_FOURCC=MJPG`、再设分辨率」；驱动只在高档位提供 MJPG（1080p 请求会被静默忽略退回 YUY2），**设完要回读确认**。这也解释了**为什么系统相机应用一直正常**：Media Foundation 自动协商压缩格式 |
| **开流会失败（防御仍在）** | ⚠️ 表现是**返回 `ok=True` 但内容全零**的占位帧（每帧固定 1000ms）。**这不是档位不支持** —— 换新句柄重开即可恢复。程序内建「有效帧判定 + 同组合重开（最多 `MAX_OPEN_ATTEMPTS=5` 轮）+ **15s 总预算**」，对低质量档位与将来换设备都是防线。⚠️ 极短时间内反复开开关（连续开关、间隔 <1s）仍会撞到这个占位态，所以 `--bench-open` 每轮之间留 0.6s，且失败信息**照原样上报**而不是静默重试到超时 |
| "好的开流"前几帧也是全零 | ⚠️ 档位越高预热越长：480p 0 帧 / 720p 1 帧 / **1080p 3 帧**。判"有效画面"时必须容许预热帧，否则会**误杀好开流**（曾因此误判"1080p 不可用"） |
| 只需 5 FPS | 采样率默认 5 FPS 是**刻意的**。坐姿变化是秒级慢过程，调高只会白耗电 |
| 判定靠相对基线 | 阈值随体型/机位/镜头变化，**绝对值不可靠，相对个人基线的偏移才可靠** |
| 暗光敏感 | 光线是影响准确率最大的外部因素，晚上必须开台灯；侧放后注意别变成侧逆光 |
| 髋部常被遮挡 | 侧面下「塌腰」需要髋部可见，写作业时经常拿不到，程序会自动跳过该项（不误报） |

| `voice.play_reminder()` | 只负责播放（语音 wav/mp3 / 提示音），**不做间隔控制**（间隔归 Gate 管） |
| `review.ReviewStore` | 判定现场图 + 指标 + 家长标注的本地存储（上限剪枝 / 一键清空 / 隐私） |
| `camera.VideoSource` / `cli.replay()` | **把录像当摄像头**，离线重跑整条判定链（标定→指标→判定→迟滞→提醒）并输出逐条时间线（`--video`）。只换帧来源，规则仍是同一份实现 |
| `logutil.RunLog` | 运行日志落盘：按天一个文件、保留最近 7 天；**写失败静默降级**，绝不影响提醒主功能 |
| `pose.shrink()` | 缩图（`PREVIEW_MAX_W`），**界面预览与审核缩略图共用**。它**不参与判定**（判定用原始帧）；审核原图另走 `full_frame`。注意 `PREVIEW_MAX_W` 一改，审核缩略图的分辨率也跟着变 |
| `ui.widgets.ScaledImageLabel` | ★ 预览绘制：**在 `paintEvent` 里按当前尺寸 × DPR 缩放**（"画面只有四分之一"的根治处，回归锁见测试组 L） |

**迟滞由 `ReminderGate` 统一实现**：单帧越界绝不报警，需连续超标 `SUSTAIN_SEC`(4s) 才提醒；
恢复正常需持续 `CLEAR_SEC`(3s) 才解除。

提醒间隔是**两道闸**，缺一不可：

| 参数 | 默认 | 作用 |
|---|---|---|
| `REMIND_GAP_SEC` | 90s | **同类**问题两次提醒的最小间隔 |
| `REMIND_GAP_ANY_SEC` | **30s** | **任意两次**提醒之间的最小间隔，**跨问题也生效** |

⚠️ 只有前者是不够的 —— 它按问题名分别计时。孩子扭一下、问题在
头前倾／塌腰／低头 之间轮换时，每个问题各自都没到 90 秒却会轮流触发，
**变成每几秒响一次**（实测踩过）。

需求原话：「三十秒之内如果提示过不正确就不提示，**即便不正确的原因也不一样**。」
—— 这正是 `REMIND_GAP_ANY_SEC` 的语义：30 秒内提醒过，就一律不再提醒，
不管这次的原因和上次是否相同。

### 坐正了不发声

**只有"需要纠正"才发声音。** 坐姿正常时程序完全静音：

- 早期在恢复正常时会 `chime("good")` 给个正反馈提示音 —— **已移除**
- 正向激励改用界面表达（绿色大字「坐得真棒！」+ 连续良好计时）
- 唯一保留的提示音是**标定完成**（`chime("done")`）—— 那是系统事件，
  不是坐姿判定，且只响一次，用来告诉家长基线采集好了

这条约束有**源码级回归锁**（测试 H1/H3），防的是以后被无意改回去。

**上面这些是防「抖一下就叫」的关键，不要为了"更灵敏"调小。**

## 已修复的坑（供参考，别再踩）

| 坑 | 症状 | 修法 |
|---|---|---|
| **侧面角度没做宽高比校正** | 16:9 下角度被压扁 44%，12° 阈值实际要求真实 21° → 系统性漏报 | 先 `* w` / `* h` 转像素再 `atan2`。回归锁见测试 B13~B15 |
| **`cap.read()` 会抛异常** | 驱动打个嗝就整个程序崩溃（实测 MSMF 报 `_step >= minstep`） | 包 `read_frame()`，异常一律当"读帧失败" |
| **采集分辨率从不设置** | 一直吃 OpenCV 的 640×480 默认值，关键点明显抖 | 显式设 `CAP_PROP_FRAME_WIDTH/HEIGHT` 到 720p |
| **躯干倾角符号写反** | `sy - hp_y` 恒为负，`trunk_angle` 永远算不出来，「塌腰」永不报警 | 髋在肩下方，取绝对值 |
| **MediaPipe 时间戳倒退** | 重标定时把 `now - t0` 归零 → VIDEO 模式时间戳倒退，推理结果错 | 时间戳基准全生命周期只设一次（`engine._t0`） |
| **迟滞逻辑写两份** | CLI 与 GUI 各写一遍，规则慢慢漂移 | 抽成 `ReminderGate`，两边共用 |
| **便携版 Python 没有 tkinter** | `import tkinter` 直接 ModuleNotFoundError，GUI 一行跑不起来 | 界面改用 PySide6；环境固定用系统 Python 3.12 |
| **pip 装 mediapipe 会撞批量删除护栏** | mediapipe 拉 opencv-contrib-python，替换 cv2 时删几千个文件被拦 | `pip install --no-deps mediapipe` + 手动补齐其余依赖，跳过 contrib |
| **Qt 布局被顶替** | `QFormLayout(page)` 会替掉该页已有布局，报 "already has a layout"，页面排版错乱 | 无父构造 `QFormLayout()`，再 `page.layout().addLayout(...)` |
| **离屏平台的字体数是 0** | `--selftest` 恒显示"系统默认"，看着像字体没选中 | 离屏模式 Qt 找不到自己的字体目录，属正常；真实运行用系统字体 |
| **提醒间隔按问题分别计时** | 头前倾／塌腰／低头 各自计时，轮流触发 → **每 4~8 秒响一次** | 增加「任意两次提醒」的全局下限 `REMIND_GAP_ANY_SEC`（**默认 30s，跨问题也生效**） |
| **坐正了会响一声正反馈提示音** | 坐姿没问题也被声音打扰（需求明确不要） | 移除该调用；正向激励改用界面表达。加了源码级回归锁（测试 H1/H3） |
| **语音播放阻塞推理线程** | MCI 的 open/close 是阻塞调用，一播语音就卡住采集循环 | 播放移入独立线程，队列深度 1（实测 say() 从上百 ms 降到 0.18ms） |
| **新语音掐断正在播的那条** | `_say_mci` 开头就 `close` 别名，频繁触发时上一条被截断（听感就是"有的没播出来"） | 单线程串行播放，同一时刻只有一条在播；入队时顶掉的是**还没开始播**的 |
| **播放失败没有任何线索** | 只报"已播放/退回提示音"，说不出为什么 | 工作线程通过 on_log 汇报失败原因（含 MCI 错误串） |
| **没给 `cv2.VideoCapture()` 加超时** | 新摄像头的 MSMF 后端**构造函数本身无限阻塞**；DSHOW 连续失败后会走到它然后**永久卡死** | 用**子进程**探测可疑后端（可硬杀）。⚠️ **不要用线程超时**——见下一条 |
| **在工作线程里创建 VideoCapture** | 拿到的是**死句柄**（只返回全零帧），表现为"有时能开有时不能"。实测 2×2：创建=主线程 4/5、创建=工作线程 **0/5** | DSHOW 走 COM，cap 绑定创建线程的 COM 单元 → **创建必须在调用线程**（读取可跨线程） |
| **单次测量给设备定生死** | 该摄像头开流有失败率，同一档位两次测量结论**相反**（一次 0/10 全黑、一次 6/6 全好），据此误判"1080p 不可用" | 不稳定设备必须**重复 N 轮取成功率**，不能单次二值结论 |
| **预热容限一刀切** | 设成 2 时 1080p 的**每个好开流都在第 2 帧被误杀**，表现为"重试四次全失败"，其实设备完好 | 按档位给容限 `warmup_budget()`（实测预热帧数 480p=0 / 720p=1 / 1080p=3，再加余量） |
| **只判 `read()` 的 ok 就选设备** | 选中"能打开但内容全零"的坏开流，画面全黑、对着黑图跑判定（每帧固定 1000ms） | 加 `frame_is_usable()`（判 `frame.max()`）；坏开流**换新句柄重开**，最多 5 轮 |
| **`except ImportError` 吞掉真病因** | 实际是 SAC 拦了 pyd，报出的却是 `AttributeError: 'NoneType' object has no attribute 'PoseLandmarker'`，排查方向全错 | 保留原始异常（`_MP_IMPORT_ERR`），在 `_need_mp()` 里带出原文 |
| **GUI 路径没做依赖守卫** | CLI 有 `_need_mp()`，GUI 走引擎绕过它，于是在 `make_landmarker` 处以 `NoneType` 炸 | 引擎里补前置检查（`pm.vision is None` → `_need_mp()`） |
| **照搬别处的后端结论** | 换摄像头后结论会**完全反转**（旧：只有 MSMF 能用；新：DSHOW 能用、MSMF 卡死），照搬会导致卡死或全黑 | 换设备后跑 `--list-cameras` 重测；判据用"能否读到有效画面"，不写死后端 |
| **HiDPI：图片只显示 1/4** | 2x 屏上预览只占左上角一块。两个坑叠加：① `QPixmap.fromImage()` 的 dpr=1.0，Qt 按 1 像素:1 **设备像素**画、不放大 → 只占一半宽×一半高；② 原写法在 `setPixmap` 时缩放到"控件**当时**尺寸"，而预览区高度会随表头文字行数回流变化，控件一变旧 pixmap 就只占一角（**时好时坏**） | 缩放搬到 **`paintEvent`**：按**当前**尺寸×dpr 缩放后再画（`ScaledImageLabel`）。任何时刻自洽、不依赖调用时序。**别在设置时固化尺寸** |
| 写死 DSHOW 后端 | 报"打不开任何摄像头"，其实设备在 | 按 DSHOW→MSMF→ANY 依次尝试 |
| 误检帧污染基线 | **画面里没人也能"标定成功"**，基线是垃圾（span=0.037） | 加合理性粗筛，拒绝不可信帧 |
| 无人的帧拉低基准 | 测出 13.2ms，实际含人要 19.2ms（乐观 40%） | 基准分开统计含人/无人帧，检出率 <50% 时主动报警 |
| 缩输入分辨率想省时间 | 实测 640px vs 1280px 只差 2.6%，白折腾 | 该降级手段已从方案中移除 |
| 手部模型降分辨率也不省时间 | 实测 1280x720 与 640x360 都是 ~18ms（内部裁 ROI） | 同上；别在这上面花心思 |
| **★ 开完流再 `cap.set()` 设属性** | 每次开流多付 **4.3s**（本机实测 `set` 三个属性 4.46s），这正是"加载很久"的最大单项 | 属性**写进构造函数**的参数表：实测 **0.17s**（快 26×）。⚠️ MSMF 不接受构造期属性 → 捕获 `TypeError` 退回后设 |
| **★ profile 做成"阶段 0 预检"** | 同一个组合要先预检一遍再走阶梯，坏开流**白付两次**代价（每次 4~7s），中位数被拖到 10.6s —— 优化措施本身成了瓶颈 | profile **只决定试的顺序**，不用来跳过验证；验证判据仍是"能否读到有效帧" |
| **★ 重试之间夹子进程探测** | 每轮 attempt 都把 MSMF/ANY 再探一遍，实测**白烧 16s** | 探测结果**落盘 + 内存缓存**，一个组合一辈子最多付一次探测代价；重试只做"同组合换新句柄重开" |
| **★ `deadline` 只管读帧，不管尝试的起点** | 「预算 15s、**22.35s 才报错**」—— 起点是预算快用完时才想起去探 MSMF，一超就 7s | 预算改成**准入闸** `MIN_ATTEMPT_SEC=2.5`：剩余不足就不再开始新一轮/不起探测。最坏情况 = 预算 + 一次读帧超时，可解释 |
| **★ 开流与读帧都发生在引擎线程里** | ① 开流的 5~20s 界面干等、没有任何进度；② `cap.read()` 在 C 层阻塞时整条循环跟着僵，界面**假死**；③ 摄像头被抢 / USB 掉线后**没有恢复路径** —— 画面停在最后一帧，程序看着还在跑 | 设备归 `camera.CameraStream`（**一条长命线程**，创建与读取同线程），引擎只"取最新帧 → 推理 → 判定"；`snapshot()["cam"]` 实时报 `opening/ready/reconnecting/failed`。另一条收益：模型构造与开流**并行** |
| **★ 降档是静默的** | 请求 4K 只拿到 1080p，程序照常跑、界面无提示 —— 家长永远不知道存证照片的分辨率掉了一档 | `OpenResult.degraded` + `warnings` 非空就必须上报：主界面黄色横幅 + 家长设置设备实况 + `--bench-open` 打 `⚠️ 降档`。测试 M3/N3/N4、界面自检都锁住了 |
| **★ 基线没绑定实际分辨率** | `sh_ear_len` 是**像素长度**：4K 标的基线拿到 1080p 下用，「低头」永远判不出来 —— 属于**漏报**，而且没有任何现象 | 基线按**实际**采集档标定与校验；档位一变（含重连后换档）立即作废基线、回「重新学习坐姿」。回归锁见测试组 N（N7~N10、N21~N23、N33/N34） |
| **★ 掉线时界面说"看不到你啦"** | 设备故障被归因成"孩子不在座位上"，家长会去挪摄像头，而真正该查的是 USB / 占用 | 断线文案改「正在自动重连」，并给出中断时长与第几次尝试；`TEXT_NODETECT` 只用于"真的看不到人"（测试 N14/N16 + 界面自检） |
| **★ 断线期间统计照加** | 没画面的时间被算进「坐得好的时间」，良好率虚高，家长看到的"今天表现很好"是假的 | 断线分支**排在统计累加之前**，`phase` 仍是 monitoring 但统计与判定都暂停（测试 N13/N32） |
| **设备把 fourcc 报成内部数值时界面吐乱码** | 家长设置里出现 `=}ë6ä`，看着像程序坏了 | `_fourcc_str()` 只接受可打印 ASCII，认不出来说「未知(0x…)」（测试 M68） |
| **家长设置里有一页是空的** | 「标定自检」结果面板被 `p5.layout().addLayout()` 放到了别的页上，p6 整页空白、p5 多出一坨 | 按页取布局：`p6.layout().addLayout(...)`。拆分界面文件时才暴露出来 —— 单文件 1300 行时没人看得见 |
